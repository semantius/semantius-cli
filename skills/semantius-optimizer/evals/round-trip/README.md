# Round-trip conformance eval (semantius-optimizer)

Offline check that the extractor (`../../references/spec-extract-lib.ts`) and the analyst's spec template (`../../../semantius-analyst/references/semantic-spec-template.md`) agree on the emitted surface, and that the extractor's output stays byte-stable.

```bash
bun evals/round-trip/check.ts            # from the semantius-optimizer skill folder; exit 0 = green
bun evals/round-trip/check.ts --update   # regenerate expected-*.md after an intentional extractor change, then review the diff
```

What it asserts:

1. **Goldens.** Every `fixture-*.json` (a JSON snapshot of the live reads: `mod`, `ownedRaw`, `fieldsByTable`, `related`, `perms` (rows the module holds), `otherPerms` (rows other modules hold), `allHierarchy`, `roles`, `processes`, `relatedModules`; the `LiveData` shape in the extractor) renders via `--from-fixture` byte-identical to its `expected-*.md`.
   - `fixture-basic.json`: an `access_scope: basic` module with a catalog entity, a workflow entity, a junction **without** a label column, a `users` built-in reference, an enum, a related module version, and per-entity permissions with every write under `manage`.
   - `fixture-custom.json`: an `access_scope: custom` module built by hand: full hand-made codes on `**View permission:**` and `**Edit permission:**`, a hand-made code the entity's edit permission names read as `narrow` (`lend`, and `write_repairs`, whose name looks per-entity), and no `entity-read` or `entity-write` row.
   - `fixture-later-embedder.json`: an `access_scope: gated` module that embeds after another module did, so `otherPerms` holds rows it does not hold. Owner-named rows reached through hierarchy rows (`ats-candidate-crm:read_candidates`, `write_candidates`, `hire_candidate`, `view_all_candidates`, a consumer's `lms-skills:read_skill_profiles`), through an owned entity's columns (`ats-offers:read_campus_offers`, `write_campus_offers`, with `**Catalog owner:**`) and through a rule (`ats-offers:cancel_campus_event`) survive; the first embedder's bundles and hierarchy rows, another module's `read` and narrow tier, and whatever sits behind them do not. It also has a gate whose verb reads like a write permission (`write_off_event`), a narrow bundle that includes a write permission, owner-named submit codes (`ats-offers:submit_campus_offer` and `ats-offers:bypass_submit_lock` cited by rules, `ats-candidate-crm:bypass_submit_lock`, on a reused entity, cited by none), a reused entity (`reuse-from hiring-starter.candidates`, no permission lines) and a computed entity at the platform default `edit_permission` `admin` (no `**Edit permission:**`).
   - `fixture-full.json`: an `access_scope: raci` module with per-entity permissions, exercising the §8.1 tier heuristic (entity-read / entity-write / narrow / override / workflow-gate (rule) / workflow-gate (lifecycle)), the admin hierarchy closure for `included in :admin?`, `high risk?` on two lifecycle gates (`deploy_asset`, cited by a living A-gate transition rule, `value_changed` on `workflow_state` with `or(is_raci_actor, has_permission)`, and included by `:admin`, so `high risk?` -; `approve_vendor`, which no rule cites and `:admin` does not include, so `high risk?` ✓), a high-risk create gate (`procure_asset`, cited by the living create guard `if($old == null, or(is_raci_actor, has_permission), true)` and not included by `:admin`), a Processes catalog, the optional §3 lines (`Order column`, `Key type` (`typeid` with `Key prefix`, and `uuid` without), `Edit mode`, `Cube mode`, `Icon`, `Label parent`), and all four §3 JSON sub-blocks.
   - `fixture-gated.json`: an `access_scope: gated` module with a lifecycle gate (`approve_request`) cited by a `workflow_state` transition rule through `has_permission`, a create gate (`create_request`) cited by the plain create guard `if($old == null, has_permission, true)`, both included by `:admin`, a `workflow-gate (rule)` code cited through `has_permission` by a delete guard, `high risk?` - on every row (not recoverable at `gated`), and the definitional `gated` Processes placeholder.
   - `fixture-family.json`: entity families and enum labels: two `typeid` bases, a `has_a` and an `is_a` entity on them (no label column / label parent lines, `**Based on:**`, the family relationship sentence, dotted §2 edges), a `has_a` entity on a base owned by another module (a `reuse-from crm.organizations` block, and the family edit grant `partners:manage → crm:manage` kept in §9.1 while an unrelated cross-module row is dropped), an enum with a `{value, label}` entry (Notes values only, a `` - `kam` `` bullet with a `  - label: Key account` sub-bullet in §5), and a `priority` enum whose entries carry `color` and `icon` (one also a `description`), stored in jsonb key order so the fixed emit order (label, color, icon, description) is exercised.
2. **Checker.** Each render passes `consistency-check.ts` (the analyst's pre-save gate / the modeler's pre-deploy gate) and contains no em-dash.
3. **Template lint.** Inside the template's "Skeleton starts below this line" … "Skeleton ends above this line" block: zero em-dashes (U+2014); every `#`/`##`/`###` heading (placeholder prefix stripped) and every table header row the optimizer is expected to emit appears as a literal in `spec-extract-lib.ts`. Table headers the optimizer deliberately never emits (§6 tables, §8.2, the RACI tables, §9.2) are listed in `NOT_EMITTED_BY_OPTIMIZER` inside `check.ts`, so the contract is explicit.
4. **Shape.** Independent of the goldens, so `--update` cannot bless a regression: every owned entity carries full codes on `**View permission:**` and `**Edit permission:**` (a computed entity has no edit line), each one a §8.1 row, and §8.1 has no `reconciliation` column. `EXPECT` in `check.ts` names the §8.1 tiers, the §9.1 rows and the rows that must stay out, for `full`, `custom` and `later-embedder`. Two variants of `later-embedder` follow: with the hierarchy rows to `ats-offers` removed, an owned entity's codes must still reach §8.1 through its columns; with an operational entity's `edit_permission` at the platform default `admin`, its line is left out.

No Semantius instance is needed. The fixtures are hand-built; keep them minimal and add a row only when a new extractor branch needs covering.

## Verifying the extractor

The authoritative output shape is the analyst's spec template (its "Skeleton" fence is the emitted surface, byte-for-byte). Read it before changing the extractor.

Run both checks after any change to `spec-extract-lib.ts` or to the spec template:

1. **Offline round-trip (always available):** this eval. It exits 0 when green. After an intentional extractor change, `--update` regenerates the goldens; review the diff before committing.
2. **Live round-trip (needs an instance):** a reference module (`it-ops-starter`) and its committed spec (`semantius/specs/it-ops-starter-semantic-spec.md`, itself an extractor output) anchor a drift check: regenerate from live and confirm every diff falls in Category B of `../../SKILL.md` or is an intentional extractor change already reflected in the goldens. A value diff outside that is an extractor defect.
